Part 1  ·  Planning Tools — Reading & Discussion (12 min)

Plans Beat Intentions

Most student teams fail their first build not because of a bad design — but because of a bad plan. They start building without knowing which part to make first, who owns each task, or when the module needs to be done. The result: two people doing the same job while a third waits for a part they haven't retrieved yet.

A Work Breakdown Structure (WBS) fixes this. It takes the full project and breaks it into phases, then tasks, then subtasks — until every piece of work is small enough that one person can own it, estimate it, and complete it. Then a Gantt chart puts each task on a timeline so the whole team can see what is happening now, what is next, and what is at risk.

Some tasks have dependencies — Task B cannot start until Task A is done. You can't attach the collector mechanism before the mount bracket is built. The chain of dependent tasks that determines how long the project takes is the critical path. If any task on the critical path slips, the whole project is late. Tasks that are not on the critical path can slip a little without delaying the end date — that slack is called float.

A milestone is not a task — it is a checkpoint. "Module attached to MiniBot" is a milestone. Either the module is attached or it isn't. Milestones tell you whether the project is on track without counting tasks.

I Do Watch the teacher model WBS decomposition and critical path thinking

Starting at the top: "The project is 'Build and test a collector module.' That's too big. I break it into four phases: (1) Design & Selection — today, (2) Gather & Prep — start of Class 8, (3) Build — Class 8, (4) Test & Iterate — Class 8 end."

Decomposing Phase 3 — Build: "Tasks: fabricate mount bracket, attach collector mechanism, wire servo/motor if needed, attach module to MiniBot, function check. Each has an owner. 'Fabricate mount bracket' = Builder, 15 min. 'Attach mechanism' = Builder + Lead Engineer review, 10 min. 'Function check' = Lead Engineer, 5 min."

Finding the critical path: "Every build task is sequential — you can't attach the mechanism before the bracket is done. So the entire build phase is on the critical path. Preparing the notebook entry, however, can happen in parallel — the Documenter can write up the design spec while the Builder is fabricating. That is not on the critical path."

The thing teams always skip — buffer: "I add 10% to every build task estimate. If a task should take 15 minutes, I plan for 17. This is not padding — it's engineering reality. In a class period, a dropped screw, a wrong-size bracket, or a misunderstood instruction each costs 3–5 minutes. Buffer absorbs these without derailing the milestone."

Part 2  ·  Weighted Decision Matrix (18 min)

Let the Data Choose

A weighted decision matrix removes personal preference from concept selection. You first set criteria — the things that matter for the design. Then you assign a weight to each criterion based on importance. Then you score each concept. The concept with the highest total weighted score is the matrix winner.

The weights must be set before you score. Changing weights after seeing the scores is bias, not engineering. The Lead Engineer owns this process and makes the final call — but they must document their reasoning, especially if they choose to override the matrix result.

I Do Watch the teacher model scoring one criterion live

Criterion: Build time (weight: 5 — highest priority, only one class period to build).

Concept A — passive funnel: score 5/5 because it needs 4 REV channels, 2 brackets, and 8 bolts. Estimated build time: 20 minutes. Weighted score: 5 × 5 = 25.

Concept B — servo claw: score 2/5 because we need to mount a servo, configure limits in software, and test the claw stroke. Estimated build time: 45+ minutes. Weighted score: 5 × 2 = 10.

Key insight: "Concept B might collect more objects per run — but if we can't build it in time, it scores zero at the challenge. The weight of 5 on build time is not arbitrary — it reflects the hard constraint that we only have one class period to build and test."

What a matrix override looks like: "If Concept B wins the matrix on every other criterion but loses badly on build time, the Lead Engineer might still choose B — but they must write: 'We are overriding the matrix result. Concept A scored higher overall but we believe Concept B's collection advantage outweighs the build time risk because we plan to start prep 5 minutes early.' That reasoning is documented. If it turns out they were wrong, the notebook shows the thinking."

Part 4  ·  Final Design Specification & Sketch (15 min)

From Decision to Build-Ready

With the concept selected and the WBS planned, you now convert the design into a design specification — a written statement of what you are building, what it must do, and every constraint it must satisfy. The spec is your build contract. If the finished module doesn't meet the spec, it isn't done.

The spec also includes the parts list — every REV channel, bracket, screw, servo, or motor needed. A good spec means your Builder can start assembling without asking the Lead Engineer any questions. If questions arise during the build, that means the spec was incomplete.
